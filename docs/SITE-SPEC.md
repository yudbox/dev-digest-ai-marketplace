# SITE-SPEC — специфікація вебдодатка каталогу (GitHub Pages)

> Специфікація UI-додатка, який публікується на GitHub Pages і дає команді шукати та переглядати вміст цього marketplace (плагіни, скіли, агенти, команди, hooks, MCP). Документ — вхід для дизайну й подальшої імплементації.

## 1. Мета, аудиторія та межі

**Мета.** Дати команді єдину точку входу, щоб *знайти* потрібний артефакт ("мені треба скіл для X"), *зрозуміти* що він робить і *поставити* його одним copy-paste. Каталог росте — UI має лишатись корисним і на 3, і на 50 плагінах.

**Аудиторія.** Внутрішня інженерна команда (dev-first). Очікують швидкий пошук з клавіатури, точні описи, робочі install-команди.

**Не-цілі v1.** Явно не робимо, бо це вимагає бекенду або ламає модель довіри репозиторію:
- рейтинги/лайки, коментарі, лічильники завантажень;
- авторизація, будь-яка персистенція користувача на сервері;
- **редагування вмісту через UI** — сайт лише читає репозиторій, ніколи не пише в нього. Джерело істини лишається git + PR-флоу (`CONTRIBUTING.md`); UI — це вітрина, не CMS.

## 2. Ключове обмеження й наслідки

GitHub Pages роздає лише статику — жодного рантайм-бекенду. Це визначає архітектуру:

1. **Пошук — клієнтський.** Індекс збирається в CI під час білду й кладеться поруч як статичний JSON. У браузері працює fuzzy + keyword (MiniSearch або Fuse.js). Жодних запитів до сервера в рантаймі.
2. **"Розумний" пошук ≠ LLM у рантаймі.** API-ключ не можна класти на публічну статику. v1 — детермінований fuzzy-пошук по описах, frontmatter і тілу markdown. Архітектура індексу одразу лишає місце під `vector`/`embeddings` (§8), щоб семантику додати без переписування фронтенду.
3. **Джерело істини — репозиторій.** UI нічого не пише. Усе, що він показує, походить з файлів у `plugins/**` та `.claude-plugin/marketplace.json`, зібраних білдом.
4. **Zero-dependency периметр CI-валідації.** `scripts/validate-marketplace.mjs` навмисно без npm-залежностей (менший supply-chain surface для workflow, що виконується проти fork PR — `on: pull_request`, не `pull_request_target`, див. `docs/SECURITY.md`). Це обмеження стосується **validate.yml**, не сайту: сайт має два окремі workflow: `site-build.yml` (на кожен pull request збирає індекс і фронтенд як build-check, **без** деплою й без секретів) і `pages.yml` (лише на `push` у `main` повторює збірку й публікує `site/dist` на GitHub Pages, ніколи проти untrusted fork-коду), тож npm-залежності фронтенду (§9) не розширюють ту саму довірчу межу. Обидва workflow-файли дотримуються вже встановленої в репо конвенції — пінити GitHub Actions на major-версію тегу, не `@latest` (`docs/SECURITY.md`, "Supply-chain hygiene").

## 3. Архітектура (загальна)

```
repo files            GitHub Actions (on push to main; окремо від validate.yml)
(plugins/**,     ──▶   scripts/build-index.mjs  ──▶  site/public/index.json
 marketplace.json,     (парсер manifest+frontmatter+md,      + graph.json
 docs/**)               агрегатор релізів, граф залежностей)  + releases.json
                                    │                          + stats.json
                                    ▼
                        схема-валідація index.json
                        (падає збірка, якщо структура не сходиться —
                         той самий принцип шаруватої валідації, що й
                         у validate-marketplace.mjs)
                                    │
                                    ▼
                            Vite build (React)
                                    │
                                    ▼
                              GitHub Pages
                                    ▲
                                    │
        браузер ◀── статичні: index.json + бандл + markdown-тіла
                    (MiniSearch у пам'яті, hash-routing, рендер MD)
```

- **Індексатор** (`scripts/build-index.mjs`) — Node, лише вбудовані модулі (той самий стиль, що й наявний `validate-marketplace.mjs`). Обходить `plugins/**`, читає manifest-и та frontmatter, збирає `index.json` (+ похідні `graph.json`, `releases.json`, `stats.json`, §4.4). Запускається і локально (`npm run build:index`), і в CI.
- **Фронтенд** — Vite + React, hash-routing (`#/...`) заради сумісності зі статичним хостингом без rewrite-правил.
- **CI/CD** — GitHub Actions, окремо від `validate.yml`: `site-build.yml` на кожен PR збирає індекс і сайт (build-check без деплою); `pages.yml` на push у `main` збирає й деплоїть на Pages.
- **Згенероване не комітимо.** `site/public/index.json`, `releases.json`, `stats.json`, `bodies/` і `site/dist/` — у `.gitignore`; їх завжди відтворює CI з git-джерел.
- **`schemaVersion` в `index.json`.** Поле `schemaVersion` (число) на верхньому рівні індексу. Захист від неузгодженості кешованого бандла й нового індексу під час деплою (напр. якщо стара вкладка лишилась відкритою під час релізу з іншою схемою) — фронтенд перевіряє версію перед парсингом і, за розбіжності, форсує hard-reload замість silent-помилки.

## 4. Модель даних (схема індексу)

Один запис індексу = один шукабельний артефакт. Тип задається полем `kind`.

### 4.1 Загальний запис `IndexEntry`

| Поле | Тип | Опис |
|---|---|---|
| `id` | string | стабільний унікальний ключ, напр. `plugin:pr-reviewer` або `skill:pr-reviewer/diff-summary` |
| `kind` | enum | `plugin` \| `skill` \| `agent` \| `command` \| `hook` \| `mcp` |
| `name` | string | технічне ім'я (kebab-case) |
| `displayName` | string? | людський підпис для UI (з manifest `displayName`, інакше `name`) |
| `keywords` | string[] | теги для фасетів і пошуку |
| `bodyText` | string | очищене від markdown-розмітки тіло README/SKILL.md — для повнотекстового пошуку (легкий payload в основному index.json) |
| `bodyHtmlPath` | string? | шлях до сирого MD для detail-view, lazy-load окремо від основного індексу |
| `sourcePath` | string | шлях у репо (для "View on GitHub") |
| `githubUrl` | string | повний лінк на файл/теку в GitHub |

### 4.2 Розширення для `kind: plugin`

| Поле | Тип | Опис |
|---|---|---|
| `version` | string | SemVer з `plugin.json` (джерело правди для версії, не git-дата) |
| `author` | `{name, email?}` | автор |
| `installCommand` | string | `/plugin install <name>@dev-digest-ai-marketplace` |
| `sourceType` | enum | `path` \| `github` \| `url` \| `git-subdir` \| `npm` (з `marketplace.json`; у цьому репо зараз лише `path`, але схема не хардкодить це) |
| `components` | `{skills, agents, commands, hooks, mcp: number}` | лічильники для картки та stats-плитки |
| `deprecated` | boolean | якщо позначено в описі за конвенцією "Deprecate, don't delete" (`docs/RELEASES.md`) — картка лишається в каталозі з бейджем, не зникає |

### 4.3 Розширення для `kind: skill | agent | command`

| Поле | Тип | Опис |
|---|---|---|
| `parentPlugin` | string | `name` батьківського плагіна — install ставить його, не компонент окремо |
| `tools` | string[]? | заявлені tools/permissions з frontmatter |
| `invocation` | string? | як викликати компонент після встановлення плагіна (напр. `/refactor`, `@react-analyzer`) — окремо від `installCommand`, бо компонент не встановлюється сам по собі |
| `model` | string? | якщо задано у frontmatter агента |

`kind: hook | mcp` не мають markdown-опису для повнотекстового пошуку (розділ 10, відкрите питання) — індексуються за назвою/типом і `parentPlugin`.

### 4.4 Похідні файли

- `graph.json` — вузли (плагіни) + ребра (`dependencies` з `plugin.json`) для фічі "Граф залежностей" (P2).
- `releases.json` — злиті CHANGELOG-и всіх плагінів + кореневий `CHANGELOG.md`, відсортовані за версією/датою, для "What's new" і майбутнього JSON/RSS feed.
- `stats.json` (або поле в `index.json`) — агреговані лічильники для stats-плитки.
- `collections.json` — **курований вручну** конфіг тематичних наборів ("стартер для React-девів") — не автогенерується білдом, редагується як звичайний контент-файл у PR.

### 4.5 Порожній стан

Зараз `plugins: []` — 0 зареєстрованих плагінів. Індексатор має коректно віддавати порожній, але **схемно валідний** `index.json` (`items: []`, `schemaVersion` заповнено), а не падати чи пропускати генерацію файлу. UI показує empty-state (§7.1), а не порожній екран чи помилку. Це вимога до першого релізу, не крайовий випадок, оскільки саме такий стан репозиторію зараз.

## 5. Функціонал (повний обсяг, з пріоритетами)

Пріоритети — для послідовності імплементації, **не** для скорочення обсягу. P0/P1 — узгоджений обсяг першого релізу; P2 — задокументовано тут, щоб дизайн і модель даних (§4) вже мали для цього місце, коли каталог доросте.

| # | Фіча | Пріоритет |
|---|---|---|
| 1 | Пошук по всьому вмісту, результати картками | P0 |
| 2 | Copy install на картці | P0 |
| 3 | Detail-view з deep-link | P0 |
| 4 | Browse + фасети (тип, keyword, author, plugin) | P1 |
| 5 | Command palette (Cmd/Ctrl+K) | P1 |
| 6 | What's new (стрічка релізів) | P1 |
| 7 | Stats-плитка | P1 |
| 8 | Онбординг "як підключити marketplace" | P1 |
| 9 | Граф залежностей | P2 |
| 10 | Collections (куровані набори) | P2 |
| 11 | Compatibility / health badges | P2 |
| 12 | JSON/RSS feed нових плагінів | P2 |

CTA "Додати плагін" (пов'язано з фічею 8) веде на вже наявний `CONTRIBUTING.md`-workflow, а не на окремий Issue Form — сайт не винаходить новий канал подачі заявок, лише вказує на процес із власною моделлю рев'ю (CODEOWNERS), що вже існує.

## 6. Інформаційна архітектура й маршрути

Hash-routing (deep-linkable, працює на статиці):

| Маршрут | Екран |
|---|---|
| `#/` | Головна |
| `#/search?q=&kind=&keyword=&author=` | Результати пошуку/фасетів (стан у URL — shareable) |
| `#/plugin/<name>` | Detail плагіна |
| `#/artifact/<id>` | Detail скіла/агента/команди/hook/mcp |
| `#/collections`, `#/collections/<id>` | Набори (P2) |
| `#/graph` | Граф залежностей (P2) |
| `#/whats-new` | Повна стрічка релізів |
| `#/getting-started` | Онбординг |

Глобальні елементи на всіх екранах: топбар (лого + глобальний search-input + кнопка Cmd+K + перемикач теми), футер (лінк на репо, версія каталогу, лінк на feed).

## 7. Екрани та UX (для дизайну)

### 7.1 Головна (`#/`)

Секції зверху вниз:

1. **Hero + пошук.** Великий інпут з плейсхолдером на кшталт "Опиши, що треба — напр. 'скіл для рефакторингу React'". Під ним — швидкі chips найпопулярніших keyword-ів.
2. **Stats-плитка** (фіча 7): N плагінів · N скілів · N агентів · N команд · N MCP. Числа клікабельні → ведуть у browse з відповідним фасетом.
3. **What's new** (фіча 6): 3-5 останніх релізів картками (плагін, версія, дата, summary).
4. **Browse-вхід**: кнопки/таби за `kind` + лінк на Collections і Graph.

**Empty-state (нуль плагінів):** дружнє повідомлення + CTA на `#/getting-started` / `CONTRIBUTING.md` ("Каталог порожній — додай перший плагін").

### 7.2 Картка артефакту (ключовий компонент)

```
┌─────────────────────────────────────────────────┐
│ [kind-badge]  displayName              v1.2.0    │
│                                                    │
│ Короткий опис у 2 рядки з ellipsis…               │
│                                                    │
│ #keyword #keyword #keyword                        │
│─────────────────────────────────────────────────  │
│ plugin · author            [Copy install] [Open]  │
└─────────────────────────────────────────────────┘
```

- `kind-badge` — колірний бейдж типу (plugin/skill/agent/command/hook/mcp).
- `[Copy install]` (фіча 2) — на плагіні копіює install-команду; на під-артефакті копіює команду встановлення батьківського плагіна **і** показує `invocation` (напр. `/refactor`), бо компонент викликається окремо від встановлення. Стан "Скопійовано ✓" на 2с.
- `[Open]` → detail-view (`#/plugin/<name>` або `#/artifact/<id>`).
- Збіг пошукового запиту підсвічується (highlight) у назві/описі.

### 7.3 Результати пошуку (`#/search`)

Список карток (7.2) + панель фасетів зліва/зверху. Лічильник результатів live. Порожній результат — окреме повідомлення "нічого не знайдено" з підказкою спробувати менш специфічний запит (не те саме, що empty-state каталогу з 7.1).

### 7.4 Detail плагіна (`#/plugin/<name>`)

Хедер: `displayName`, version-badge, `kind`, `author`, compatibility-badge (P2), кнопки Copy install і View on GitHub. Тіло: рендерений `README.md` плагіна, список вкладених компонентів (кожен — мініатюрна картка 7.2, клік → `#/artifact/<id>`), `dependencies` (граф — P2).

### 7.5 Detail артефакта (`#/artifact/<id>`)

Хедер: `kind-badge`, `displayName`, посилання "частина плагіна `<parentPlugin>`". Тіло: рендерений `SKILL.md`/опис агента чи команди, `tools`, `invocation`. Кнопки Copy install (батьківського плагіна) і View on GitHub.

### 7.6 What's new (`#/whats-new`) і Getting started (`#/getting-started`)

Повна хронологія релізів із `releases.json`, лінк "Subscribe" → JSON/RSS feed (P2). Getting started — рендер кроків підключення з copy-кнопками, узгоджено з `README.md`: `/plugin marketplace add yudbox/dev-digest-ai-marketplace`, `/plugin install <name>@dev-digest-ai-marketplace`, різниця `marketplace update` vs `plugin update`.

## 8. Поведінка пошуку (v1: fuzzy + keyword)

- Рушій: MiniSearch (або Fuse.js) у пам'яті, індекс будується з `index.json` один раз при завантаженні.
- Шукані поля з вагами: `displayName`/`name` (найвища) → `keywords` → `description` → `bodyText` (найнижча).
- Prefix-match під час набору тексту, fuzzy-толерантність (1-2 одруківки), highlight збігів, буст точних збігів імені.
- Фасети застосовуються як пост-фільтр над результатами (AND між різними типами фасетів, OR усередині одного).

**Закладено на майбутнє (не v1): embeddings-ready архітектура.** Поле під вектор передбачене в схемі (§4) для можливого апгрейду — у CI генеруються embedding-вектори для `description`/`bodyText`, у браузері рахується косинусна близькість. Окрема ітерація; спосіб векторизації запиту користувача — відкрите питання (§11).

## 9. Технічний стек

| Шар | Вибір | Причина |
|---|---|---|
| Фронтенд | React + Vite | компонентний, звичний команді, легко рости під P1/P2-фічі |
| Мова | TypeScript | типізований `IndexEntry` (§4), менше помилок при рості схеми |
| Пошук | MiniSearch / Fuse.js | клієнтський fuzzy, малий бандл |
| Роутинг | hash-router (light) | статичний хостинг без rewrite-правил |
| Рендер MD | `markdown-it` / `marked` + sanitize | detail-view README/SKILL.md |
| Граф (P2) | легка graph-viz (напр. `@xyflow/react` чи `vis-network` — уточнити на дизайні) | фіча 9 |
| Індексатор | Node, лише вбудовані модулі | у стилі наявного `validate-marketplace.mjs`, без npm-залежностей |

## 10. Відомі обмеження

- **Hash-routing → немає per-route соціальних meta-тегів.** Посилання на конкретний `#/plugin/<name>` в Slack/Discord завжди розгорнеться з загальними OG-тегами головної сторінки (fragment не йде на сервер). Це прийнятний trade-off для внутрішнього dev-first інструменту, але варто знати наперед, а не виявити після релізу.
- **Мобільна адаптивність — вторинний пріоритет**, не блокер: аудиторія переважно desktop + клавіатура (Cmd+K), але картки й пошук не повинні ламатись на вузькому viewport.
- **Базова доступність**: клавіатурна навігація по картках і command palette, достатній контраст кольорових `kind-badge` — мінімум, а не окрема P2-фіча.

## 11. Свідомо поза межами v1

Крім P2-фіч із §5 (граф залежностей, collections, compatibility badges, JSON/RSS feed):

- Popularity-сигнал через GitHub API (stars/issues) — rate limits ускладнюють надійність.
- Embeddings-пошук (§8) — архітектура готова, увімкнення відкладено.
- UX для `renames`-map з `marketplace.json` (стара назва → редирект/примітка) — за замовчуванням build просто бере поточний `name`, без спеціальної обробки старих посилань.

## 12. Відкриті питання

- Індексація `hooks/hooks.json` і `.mcp.json` (§4.3) — без markdown-опису повнотекстовий пошук неможливий: індексувати лише за назвою/типом, чи вимагати опис у сусідньому README?
- Хто рев'ює зміни до самого сайту (`docs/SITE-SPEC.md`, фронтенд-код) — той самий catch-all CODEOWNERS (`@yudbox`), чи окремий власник для UI-частини репозиторію?
- Векторизація пошукового запиту користувача для майбутнього embeddings-режиму (§8) — чи можлива повністю client-side, чи потрібен легкий проксі.
- Схема-валідація `index.json` перед деплоєм (§3) — окремий крок у `site-build.yml` / `pages.yml`, чи частина самого `build-index.mjs` (fail fast у скрипті)?
